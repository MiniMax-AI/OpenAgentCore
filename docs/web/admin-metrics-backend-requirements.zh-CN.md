# 管理员指标：后端需求

状态：待与 Core 负责人讨论的提案，本文所列内容均未实现。[English](admin-metrics-backend-requirements.md)

新版控制台以运维为先：总览、智能体监控、沙箱监控、会话日志。目前所有数字都由浏览器用现有接口读出后自行汇总。本文说明这样做的代价、哪里不完整，以及哪些 Core 接口可以替代浏览器端的计算。

## Core 的两类接口

1. **面向用户的 Agents API**（`/v1/agents/**`、`/v1/vaults/**`、`/v1/files**`、`/v1/skills/**`）：必须与锁定版本的 OpenAI Agents API 及已记录的 Core 扩展保持一致。指标相关工作不得在这里新增字段、路由或行为。
2. **仅供控制台使用的管理接口**（`/core/v1/**`）：部署级路由，只由已登录的配对控制台用服务端的部署管理员令牌调用。`sandbox` 和 `project-api-keys` 已在这里。下文提议的所有接口都属于这一类，并需要加入控制台的转发白名单（`services/core-console`）。

现有 `/v1` 下供 Web 使用的 Core 扩展（运行时观测、运行时历史、启动配置、执行配置、沙箱放置）保持不动，本提案不迁移它们。

## 控制台目前如何计算

| 页面 | 数据来源 | 限制 |
| --- | --- | --- |
| 总览、会话日志、智能体 | 完整会话列表与运行时观测，每 30 秒重读 | 约 1 万个会话；仅限控制台凭据所属项目 |
| 智能体监控 | 时间范围内最近活跃会话的 Turn 与 Item | 每次最多 200 个会话，每个会话最多 10 页 Turn、5 页 Item，每个会话限时 15 秒、每次加载 45 秒；每个会话 1 到 15 个请求，最坏情况下每次刷新约 3,000 个请求 |
| 沙箱监控 | `/core/v1/sandbox` 的节点与分配；按托管会话读取运行时历史 | 主机指标只有可用内存/磁盘和 CPU 核数；历史最多覆盖 24 个托管会话 |

控制台在问号提示和告警中说明的后果：

- 汇总只覆盖一个项目（控制台的项目凭据），不是整套部署。
- “请求”指智能体 Turn。HTTP 层面的请求数、状态码和 API 延迟目前都拿不到。
- 模型归属来自会话的智能体快照，而不是实际生效的执行配置。
- 繁忙部署会超过会话上限，长时间范围的数据不完整。

其他限制：浏览器与 Core 的时钟可能不一致（控制台默默容忍 15 分钟偏差，不在页面上提示）；不统计子智能体 Turn 和已删除的会话。

## 建议新增的接口

所有接口只读、部署级，可选 `project_id` 过滤；像运行时历史一样有边界（`start`、`end`、`step`、最大时间范围与点数）；不可用的值返回 `null`，不返回 0。这些是运维证据，不是计费依据。

### P0：智能体运行聚合

`GET /core/v1/metrics/agent-runs?start=&end=&step=&group_by=model|agent|harness|project&project_id=`

每个时间桶（设置 `group_by` 时再按分组）返回：

- 创建、完成、失败、取消、仍在运行的 Turn 数。
- 从 `started_at` 到 `completed_at` 的耗时：平均、p50、p95。
- 从 `created_at` 到 `started_at` 的排队时间：平均、p95。
- Token：输入、输出、缓存输入、推理。
- 来自执行配置的实际模型与执行引擎。
- 前 N 个分组加一个 `other` 桶，以及分组总数。

它可以替代智能体监控页逐会话读取 Turn 的做法，并让长时间范围的数据完整。

### P0：工具调用聚合

`GET /core/v1/metrics/tool-calls?start=&end=&step=&group_by=tool|kind|agent&project_id=`

按时间桶和工具（`function` 名称、MCP 的 `server_label` 加名称、Shell 命令、网页搜索、子智能体）返回调用数、失败数，以及 Item 上报时的耗时。它可以替代逐会话读取 Item。

### P1：会话汇总

`GET /core/v1/metrics/sessions?project_id=`

按状态、环境类型、智能体统计的数量，以及每个时间桶新建和活跃的会话数。总览可以不再读取完整会话列表。

### P1：Agents API 请求指标

`GET /core/v1/metrics/api-requests?start=&end=&step=&group_by=route|status_class|project`

由 API 路由中间件记录：按路由族（会话、事件流、Turn、Item、文件等）统计请求数、4xx/5xx 数和延迟分位数。这就是托管平台控制台里的“请求数”和“错误率”。建议参照运行时历史，把汇总写入现有 PostgreSQL 并设保留期，可选 OTLP 导出作为第二去向。

### P1：节点利用率与历史

- 在 `GET /core/v1/sandbox/nodes` 中增加：主机 CPU 利用率、内存已用与总量、磁盘已用与总量、节点软件版本、进程运行时长。
- `GET /core/v1/sandbox/nodes/{id}/history?start=&end=&step=`：活跃、保留、预留沙箱数和主机利用率随时间的变化。

### P2：部署配置写入

控制台目前只能读到每个执行引擎在启动时是否配置了模型端点。仅供控制台使用的写接口（例如 `PUT /core/v1/deployment/model-providers/{harness}`，凭据只写）可以让运维在 Web 上设置部署默认值。优先级必须保持“会话 → 智能体 → 部署”，且绝不返回密钥。

### P2：密钥与项目

- API 密钥的 `last_used_at` 和按密钥统计的请求数。
- 如果一套部署服务多个项目，提供项目列表（`GET /core/v1/projects`），以便在 Web 中按项目筛选指标。

## 待讨论问题

1. 聚合是读取时从现有表计算（简单，但大部署会慢），还是周期汇总（参照运行时历史）？
2. 每类指标的保留期和最大时间范围分别是多少？控制台用 7 天是否足够？
3. 各类指标统一使用哪种分位数算法和时间桶对齐方式？
4. 实际部署是否会有多个项目？节点分配里其他项目的会话 ID 谁可以看到？
5. API 请求指标是否要排除控制台自身的轮询流量？
